## 新发现：哪些必须修、为什么

### A. 验证器会在特定运行模式下给错误 SQL 出具通过报告

在临时提交副本，将正式 GMV 的 `SUM(price + freight_value)` 改成 `SUM(price)`。普通 Python 运行真实 MySQL 反例脚本返回 1、报告 failed；相同代码用 `python -O` 返回 0、报告 passed，还声称错误变体已被数值断言拒绝。

原因可从实现核对：大量关键验收使用 assert，-O 禁用这些语句；部分“已捕获”字段随后直接写 True。这是**证据机制缺陷**，不是说正常 Python 下此前真实月度数值错误。

修复方向：验收入口显式拒绝优化模式；关键放行条件使用不会被优化删除的异常检查；从实际观察生成捕获结果。再次验收必须重放同一个缺运费变体，正常模式拒绝，-O 要么明确拒绝运行，要么仍检测失败，任何路径不得写出 passed。

### B. 配置与数据库生命周期耦合，复现不是只复制代码

同宿主机保留项目 MySQL 容器，导出新 checkout，不注入原 `.env`。运行初始化实际约 94.53 秒后退出 1，报 MySQL 未就绪。新 checkout 生成了新随机配置，但固定名字的旧容器仍使用旧凭据；代码把认证失败与启动等待混在一起。

正常副本在明确注入原配置时可运行，故不能把该结果外推成“全新机器一定失败”。但它已否定“现有环境随便换目录仍可从零跑通”的假设。

修复方向：明确新建实例、复用实例、凭据缺失/错误三种路径；可配置连接端点及实例标识；认证错误快速诊断，不盲等、不覆盖旧配置、不删卷解决。再次验收至少覆盖全新受控实例、同实例重跑、新 checkout 复用、凭据缺失和端口冲突，确认原实例数据不被破坏。

### C. 失败状态与旧产物之间缺少统一交付清单

成功生成月度结果后，同一输出目录改用缺输入运行。命令确实返回 1，查询被 blocked_dependency 阻断；但上次的 q2_2_results.json 仍存在且摘要不变。不能谎称这次“失败仍返回成功”，真正问题是单独拿文件的人无法仅凭目录判断它是不是本次结果。

修复方向：引入 run_id 的产物目录和统一 manifest，绑定代码、输入、状态和每份输出摘要；失败时明确标旧，或只在整批成功后更新当前成功索引。保留旧成功结果本身并非错误，缺少清晰归属才是风险。再次验收要求消费端拒绝把旧文件当本次失败运行的结果。

### D. 多代验收规则并存，指南不是可靠的唯一入口

本轮实际运行旧 stage_gate：单元、baseline、mutations 和保护文件检查通过，但 clean_environment 源码指纹过期，整体返回 1。新 Q2 链路则允许按未变 requirements 复用安装证明。这两者检查的不是同一范围，旧脚本仍提示“允许进入 Q1.1”，容易被当成当前总门槛。

修复方向：分开“依赖安装有效性”“当前代码功能验收”“整项目交付完整性”，提供唯一当前入口和需求清单。历史门槛改为明确历史用途，不能删掉失败历史或直接修改报告为 passed。再次验收要证明缺模块、旧源码、错产物、缺证据分别会失败，并给可理解原因。

## 优化方向也需要改变

当前风险不是再缺几个相似数值测试，而是大块必答功能尚未交付、Q4 外部约束尚未验证。逐小改动全链重导入九表能提高追溯性，但不是唯一合理策略：将快速契约测试、受影响模块集成、发布前全链验收分层，以输入/代码/模式版本判断证据可复用范围，不能用硬编码测试数量判定质量。

当前审查报告目录约 1.47 MB（本轮盘点时），没有证据表明体积已经成为性能问题；问题主要是导航和有效性，优先做索引，不先删历史报告。

Q4 的原始数据初查为低分记录 22,754 条，其中正文空白 8,309、有正文 14,445；review_id 额外重复 261 行。不能按题目“约 1–2 万条”估价，也不能只按 review_id 丢弃记录。这是一次原始 CSV 初查，尚未构成抽取准确率、费用或耗时证据。
