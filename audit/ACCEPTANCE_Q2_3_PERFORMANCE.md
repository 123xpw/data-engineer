# Q2.3 保持口径的性能实验：先定验收

基线为本地候选 `0f4088994a531209dc3aeaec7732cef83566fdd8` 的 Q2.3 SQL。先将其原样冻结在 `audit/fixtures/`，候选仅将三个内连接改为 STRAIGHT_JOIN。筛选、LEFT JOIN、评价排序、聚合、运费、分母、州内排名和 TOP20 稳定顺序均不改变。

## 必须同时通过

1. 基线与候选都通过既有手算、并列排名、同人多客户标识、多商品、多评价、缺送达时间、跨卖家和定向错误测试。
2. 全部卖家每一列及顺序均与原始 CSV 的独立 Decimal/字典参考一致；每轮测量都检查。另执行真实 TOP20，与独立参考及原规范结果一致。
3. 获取导入互斥锁，同一 ready 数据批次内串行测量。双方先各执行一次 EXPLAIN ANALYZE 预热，保存真实迭代器计划；该耗时不纳入性能比值。随后按旧/新、新/旧、旧/新的顺序各测三轮完整卖家查询，时间包括执行、取回及规范化。
4. 每个查询设服务端 180 秒上限；超时按失败记录，不延长上限制造达标。新中位耗时 <= 旧中位的 80%，新最慢一轮 < 旧最快一轮。缺任一轮、错误结果、警告、批次或 SQL 变化均不通过。
5. 先实测通过，再将候选采用到生产 SQL；验收器核对冻结 SQL、数据/依赖、实验代码、每轮观测和重新计算的统计量，过期或缺失时拒绝。
6. 采用后冻结源码，重跑所有受影响回归和最终完整入口；旧成功报告不继承为当前通过。Q4 使用现有真实缓存，零新增模型请求。完整提交门槛继续拒绝人工/账单/日志/发布等未闭环事项。
7. 最终检查拟提交材料、凭据和可达历史，保留原失败及既有模块提交，仅本地提交，不推送。

## 允许得出的结论

只证明本机、当前冻结规模与配置下，完整卖家查询在暖缓存对照中的观测变化；不能推断冷启动、百倍规模、其他硬件或统计信息变化后的表现。STRAIGHT_JOIN 限制优化器选择，未来数据分布/模型变化时应重新比较。Q2.4 原题的等价优化仍未证明提速，本实验不替换其结论。

来源：[MySQL 8.4 JOIN](https://dev.mysql.com/doc/refman/8.4/en/join.html)、[外连接优化及 STRAIGHT_JOIN 的限制](https://dev.mysql.com/doc/refman/8.4/en/outer-join-optimization.html)。

## 预检反证与第二版候选（正式对照计时前补充）

第一版仅改三个内连接，完整卖家及 TOP20 正确性预检通过，但完整查询实测 100.180801 秒，估计计划仍先连接不直接相关的卖家与订单。没有正式三轮对照，不能称为已经达成性能门槛。保留该预检报告和第一版 SQL，不采用到生产。

第二版在第一版基础上增加 `NO_MERGE(facts)`，隔离事实 CTE 的查询块，再观察内部连接顺序是否保留。候选为 `audit/fixtures/q2_3_materialized_candidate.sql`；允许变化明确限定为三个内连接操作符和这一个提示，业务表达式不变。采用门槛、计时轮数、超时及语义标准全部不变。实测前先核对计划及提示警告，再重新预检。

参考：[MySQL 8.4 派生表/CTE 合并与物化](https://dev.mysql.com/doc/refman/8.4/en/derived-table-optimization.html)。物化可能增加临时存储开销，不能只凭计划变了就宣称更快。
