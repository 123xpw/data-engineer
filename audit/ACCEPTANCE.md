# 整项目交付审查：执行前标准

本轮冻结审查基线为 Git HEAD e6937ad，原始标准来自邮件、根 README 和各题要求；旧指南/通过报告均作为待核实对象。用户已确认目标为能否正式交付。此次先定位和排序问题，不直接扩展业务功能，也不改写过去的决定与失败历史。

## 必须区分的三个结论

1. **项目可交付**：必答模块、完整入口、必填文档、公开 Fork、最终版本、真实评估/成本/性能材料均满足或用户明确接受部分提交。当前缺项不能被已完成模块的测试抵消。
2. **已实现部分可验收**：按其声明范围验证数值、异常、独立运行和复现；不自动等于可以正式提交。
3. **验收证据可采信**：必须知道测试的代码、输入、环境、实际命令和输出；不根据报告中的 passed 字段直接认定正确。

## 本轮预先安排的实验

| 实验 | 执行方式 | 判断规则和限制 |
|---|---|---|
| 原题逐项交付盘点 | 检查实际受 Git 跟踪的文件、模板占位和入口分支 | 文件存在不等于内容完成；Q5 只需设计，不要求部署实时系统 |
| 提交副本完整入口 | git archive HEAD 导出，外部 cwd，复用明确标记的真实输入/既有 Python/MySQL 配置 | 保存实际退出码及阶段状态；退出 2/partial 不能认定整项目完成；不是全新操作系统冷启动 |
| 副本单元测试与直接入口 | 使用提交中的代码，不调用旧完整验收脚本自证 | 测试成功只覆盖各测试目标；缺失模块明确记未测/未实现 |
| 失败后产物归属 | 成功输出后，在同一目录以缺输入运行，比较退出码与产物摘要 | 若旧结果保留，需要判断是否有清晰运行版本关联，不能谎称失败命令返回成功 |
| 不注入私有配置的副本 | 已有本项目容器的同一宿主机，移除配置注入，使用新的本地配置路径 | 检验多 checkout/恢复场景；不得外推成全新宿主机必失败；不停止或删除现有数据库 |
| 验证器反向检验 | 临时副本将 GMV 去掉运费，分别普通 Python 与 -O 执行同一个真实 SQL 反例脚本 | 普通运行须拒绝错误；若优化模式放过，记录运行条件，不把非默认模式风险说成默认结果错误 |
| 旧指南门槛有效性 | 当前源码实际运行现有 stage_gate | 记录是否过期或不可用；不把历史门槛的失败自动当作业务数值失败 |
| 决策可解释性 | 回看原始可见对话与 Git 历史，记录选择、替代方案、当时证据、现在局限 | AI 不替候选人声称已掌握；未找到记录的动机标为待确认 |

## 判定与后续安排

交付结论采用 blocking / conditional / satisfied / unverified，不计算“通过数量百分比”冒充完成度或得分。将未实现、真实缺陷、证据不足、可选优化分开。关键发现须给复现、影响、修复建议和再次验收条件。尚未完成全项目前，不发布、不发邮件、不创建替代空仓库。
