## 本轮修改

实现 MySQL 8 CTE/窗口函数查询，先汇总卖家/订单、每订单确定性选择一条评价、完整州内 RANK 后取平台 TOP20；独立 CLI 和 `run_all.py --stage q2.3` 走产物清单发布。JSON 公开评分和物流分母，中文报告说明无法归属订单与业务选择。SQL 尚未完成性能优化。

## 实际核验

- 人工样例先固定预期，再在连接内临时表执行；多商品、多卖家、重复评价、客户跨订单、取消、缺时间、并列与 TOP20 边界通过。省略运费、评价不去重、用 customer_id 统计客户、全平台排名冒充州排名四种 SQL，均以具体数值差异被识别；SQL 执行错误不计为捕获。
- 补充样例确认零 GMV、无评分/无有效时长返回 NULL、2017 年严格半开区间、等于预计日期不算延迟、同日期/ID 评价按来源行稳定选择。
- CSV/字典/Decimal/datetime 独立复算全部 1,784 位卖家，逐列比较全部结果及 TOP20。2017 年订单 45,101 张，可归属 44,579 张；未归属 522 张，其中取消 61 张。已送达价加运费合计 6,921,535.240，与 Q2.2 的 2017 年月度之和相同。该一致性不能证明退款净收入。
- 72 位卖家的平均评分随最新、最早或每订单均分规则变化。例如 4.169811 / 4.150943 / 4.160377。这个差异说明治理选择会影响结果，不代表其中一种已获业务认证。
- 独立 CLI 与单题总入口业务结果一致；缺输入时清单 blocked_dependency，旧产物被拒绝。已有 Q1、九表、Q2.1、Q2.2 当前源码完整回归通过。

## 本轮失败与修正

首先发现 MySQL SUM 的 Decimal 被通用转换成字符串，计数类型违反预期；改为显式整数列集合。首次失败后修改代码时原验收进程还在执行，源码变化守卫拒绝后续发布；改为关键前置失败就停止，再冻结源码另起完整验收。不能把这类执行安排错误归因于外部环境。

修改前还修订了一条错误的测试预期：同 GMV 排序下先平台 TOP20 后州排名可能数值相同，因此未声称捕获该变异，改测明确的全平台排名错误。测试预期也应接受质疑。
