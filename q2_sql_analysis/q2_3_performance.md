# Q2.3 连接计划优化：实测、口径与限制

**已通过采用门槛；全项目回归另看最新 release 报告。** 验收标准在实测前冻结，见 [验收契约](../audit/ACCEPTANCE_Q2_3_PERFORMANCE.md)。本题是额外发现的 Q2.3 运行成本问题，不能混称为 Q2.4 原题的提速。

## 改了什么，为什么这样改

保持所有筛选、运费、评价选取、分母、州内排名及 TOP20 排序不变。三处内连接使用 STRAIGHT_JOIN，并通过 NO_MERGE(facts) 保留事实 CTE 的查询块；只改变物理计划选择，不新增表、索引或依赖。

第一版只改内连接，手算、全部卖家及 TOP20 预检正确，但查询仍耗时 100.180801 秒，估计计划仍先连接卖家与订单；没有正式对照，未采用。第二版再隔离 facts，预检 2.259995 秒，随后才进入正式三轮对照。第一版 SQL 和预检报告保留，不能把第一版“预检通过”当作性能通过。

## 实际三轮对照

同一 ready 数据批次持有导入互斥锁，双方分别执行 EXPLAIN ANALYZE 预热后，再按旧/新、新/旧、旧/新交替。下表测量完整卖家查询，已去掉最终 LIMIT 20；时间包含取回与规范化，每次都将 1,784 位卖家的全部字段和顺序与原始 CSV 独立参考比较。TOP20 另执行并核对。

| 轮次 | 基线秒 | 候选秒 | 先后顺序 |
|---|---:|---:|---|
| 1 | 101.444711 | 2.293888 | baseline → candidate |
| 2 | 99.330081 | 2.360676 | candidate → baseline |
| 3 | 99.875974 | 2.363538 | baseline → candidate |

中位数由 **99.875974 秒**降至 **2.360676 秒**，比值 **42.31**。候选最慢 2.363538 秒，仍快于基线最快 99.330081 秒，达到预定的 20% 改善和区间不重叠门槛。

[正式回执、六次原始观测及双方实际计划](../reports/q2_3/performance_45f38cd43a96458db72301b7a7c40d08.json)；实验代码见 [q2_3_performance.py](../audit/q2_3_performance.py)。预热分析耗时未算入加速比，未丢弃慢样本或改变门槛。

实际计划显示基线存在 no condition 的 hash join，输出约 1.4 亿个中间组合，后续才经明细关联收敛为 45,078 个事实行。采用版物化 facts 后先关联明细与订单，避免这项放大。估计成本不能替代真实迭代器和计时；计划中的行数估计存在明显失真。

## 如何避免以后用过期证据放行

正式题目验收与 release 检查均复核实测 SQL、协议代码、契约、类型视图、依赖和输入指纹，并从六次观测重新计算统计量。性能实验代码和冻结材料也纳入整体验收指纹。修改后必须重新验证；预检报告的范围标识不能冒充正式实测。另以篡改汇总、缺轮、旧 SQL 指纹、预检替代四类损坏记录做拒绝控制；这些控制不代表能识别所有伪造。

## 限制与替代方案

本结论只适用于本机、当前 MySQL 8.4 与冻结数据规模的暖缓存完整卖家查询；不是全入口加速比、冷启动保证或百倍数据证明。原始 CSV 的独立参考仍共享由本项目选择的业务口径，不是另一位独立人员审查。

固定顺序会减少优化器选择，物化会引入临时存储开销，本轮未测峰值内存。未来数据分布、类型视图、MySQL 或硬件变化，应重新比较默认计划。可选方案包括局部连接顺序提示、保留原始层之外的类型化分析表或表达式索引；本轮未将未实测方案写成更优。
