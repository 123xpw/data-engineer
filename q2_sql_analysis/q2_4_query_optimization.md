# Q2.4 慢查询分析、统计修正与真实实验

本题按原始 SQL 的 delivered、下单时间 >= 2017-01-01、LOWER(city) 含 sao 筛选，包含 2018 年；不是 Q2.3 的仅 2017 年。当前冻结数据选中 20,367 张订单、22 个州。最新评价选择沿用 Q2.3 的确定性规则，仍属于治理假设。

## 至少三个性能问题及原因

1. `LOWER(customer_city) LIKE '%sao%'` 同时有函数和前导通配符。即使移除 LOWER，普通 B-tree 也不能据前导通配符构造前缀范围；将条件改成 `= 'sao paulo'` 会改变原题范围，手算已证明漏单。固定业务可考虑维护版本化的布尔搜索属性及索引；通用子串搜索需要不同检索策略，不能直接用全文分词代替。
2. 订单明细和评价均为一对多，直接连接扩大中间行，COUNT DISTINCT 只修复订单计数，还增加去重成本；金额和 AVG 的权重仍错。先将商品聚合到订单，评价每订单明确选取一条，再 COUNT(*) 可减少中间粒度并修正统计。
3. 本项目分析视图把原始键包装在 NULLIF 等表达式中，联接与过滤不能简单等同于原始列索引访问。当前计划中可看到全扫描与 hash join；估计基数极大，但实际执行并没有同等数量的记录。候选以经过完整类型/键验证的原始等值键联接，金额显式 CAST，避免隐式数值转换。生产更适合建立类型明确、物理键受约束的分析表。
4. 全量评价先窗口排序再连接会处理不相关订单。修正版先选目标订单，再聚合商品和评价；目标 CTE 明确 DISTINCT，固定订单粒度并阻止直接合并。是否物化、自动索引或复用由实际计划核查，不能仅凭 CTE 写法说必然更快。

最后按收入排序只处理当前 22 个州，不应把这一步夸大为本例主要瓶颈。

## 三个可核对的 SQL 版本

- [原题 SQL](q2_4_original.sql)：忠实保留连接扩增和评价权重。
- [等价执行候选](q2_4_equivalent.sql)：在冻结原始格式、键关系成立时保留原结果，用于纯执行路径对照，不是业务正确答案。
- [业务修正版](q2_4_corrected.sql)：商品先聚合到订单、每订单选择一条评价。输出 price_revenue 只含商品价格，保持原题 SUM(price) 的金额范围；未添加运费，也不命名为退款后净收入。缺明细/未知价格有诊断，正式发布拒绝静默忽略异常。

## 索引和模型建议

当前原始表已有各 ID 的前缀索引；不能重复宣称“新增联接索引”已带来收益。可进一步评估：

```sql
-- 可评估的原始层候选，尚未创建或证明提速；每次导入重建原表后需配套管理。
CREATE INDEX q24_status_date_customer
ON raw_orders (order_status(16), order_purchase_timestamp(19), customer_id(32));
```

该候选只适用于已验证的规范时间字符串；状态/时间在本数据上的选择性可能很低，未必被选择，也增加写入和存储成本。生产类型表可考虑 (order_status, order_purchase_timestamp, customer_id)，日期应为 DATETIME。商品订单键索引已有；类型表上的 (order_id, price) 才可能形成金额读取覆盖，不能把当前 VARCHAR 前缀索引冒称为完整覆盖索引。评价排序键的复合索引也须结合窗口计划再评估。

[MySQL 范围优化说明](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html)说明 LIKE 前缀范围条件；[生成列索引说明](https://dev.mysql.com/doc/refman/8.4/en/generated-column-index-optimizations.html)说明表达式索引的适用规则。索引建议并未替代实测。

## 当前规模实测：未证明执行候选更快

一次暖机不计入；同连接、同批次、三轮交替顺序，取客户端执行/取回/警告核验的中位耗时。测量期间持有项目导入锁，没有并行导入；不是新机器、冷缓存或百倍规模。

| 版本 | 三轮中位秒数 | 与哪个答案比较 | 结论 |
|---|---:|---|---|
| 原题 | 0.206245 | 独立 CSV 重现原题结果 | 原查询确实会扩增金额 |
| 等价候选 | 0.222269 | 与原题全部州全部列相同 | 当前未证明提速 |
| 业务修正版 | 0.269226 | 独立 CSV 按订单复算 | 语义已经改变，不计算纯优化倍数 |

没有为了制造漂亮对比强制禁用原查询优化器。当前原查询本来已较快，计划估计成本下降不能当作实际提速。题目所称 100 倍数据由 2 秒变 5 分钟是给定情境，本项目没有生成/执行百倍数据，不能将本机结果外推。

真实计时及 EXPLAIN FORMAT=JSON/EXPLAIN ANALYZE 原文见 [实验制品](../reports/q2_4_experiment.json)，通过记录编号 `2369f28ece40408f8f4e480431eff880`。JSON 估计行数与 ANALYZE 的实际迭代器 rows/loops 分开存放，没有填造一个“扫描总行数”。重复计时范围不构成严格统计显著性结论。

## 统计错误与逐州独立复算

固定手算：A 单两件价格 10+20，两条评分 1/5；B 单价格 40，一条评分 4。直接连接订单数仍为 2，但金额为 100、评分 3.2；修正后金额 70、每订单最新评分均值 4.5。COUNT DISTINCT 无法同时修正 SUM 与 AVG。

真实 SP 州原查询商品价格合计 2,229,221.290，订单粒度修正为 2,217,437.430；评分分别为 4.1829 与 4.246310。这不是同一口径下的优化前后“应该相等”。等价版本与原版本相等，业务修正版与独立 CSV 字典/Decimal 参考相等，全部 22 个州逐列检查。

同一订单可能重复评价；缺评价不填零。商品价格未含运费，若业务需要 price+freight GMV 须另改口径；退款、取消、支付结算也不是此查询认证的净收入。多条评价怎样选仍需业务确认，详见 Q2.3 敏感性实验。

## 实验限制与失败

手算最初触发 MySQL 1137（重复打开同一临时表），并未算作捕获统计错误。后改为固定常量 CTE 承载原始层夹具，保留原查询的类型层临时表；正式查询不创建或修改业务原表。当前实测未获得提速，是必须保留的结果。正式入口与当前全项目门槛需另行通过，不能只凭本文宣称可提交。
