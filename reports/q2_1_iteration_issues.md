# Q2.1 本轮迭代中实际发现的问题

## 真实数据与题目预设

初查发现 2 个有名未译类别：portateis_cozinha_e_preparadores_de_alimentos（10 个商品）、pc_gamer（3 个商品），另有 610 个类别为空的商品。“3 类”不能当硬编码答案，也不能把空类别伪装成一个名称。最终数值以通过的独立核验报告为准。

review_id 的额外出现为 814 条、order_id 在评论表额外出现为 551 条；地理邮编也非唯一。这否定了直接加单字段唯一键并忽略冲突的导入方式。保留来源行主键，后续评价去重与地理聚合另立用途规则。

## SQL 空白英文遗漏（已修正，失败证据保留）

首次真实 MySQL 临时表实验中，仅普通空格构成的英文被初版 `english <> ''` 当成有效翻译。预先写定的手算期待包含 spaces 类，实际缺少它，断言失败：sql_cases_1a8f598741984b379e2d63083c0b153c.json。

修改为 `TRIM(english) <> ''` 后同一反例通过。TRIM 仅用于有效性判断，未覆盖原始值；类别名仍保留尾空格与大小写。其他 Unicode 空白不自动规范化，属于明确边界。本次没有以真实数据没有该例为理由跳过修复。

## 独立验证器遗漏 UTF-8 BOM（已修正，失败证据保留）

首次全量验收的九表独立往返、金额、键及关系检查通过，但真实查询参考计算触发 KeyError：acceptance_6616b53464d24b3eb3981ed29bf9a297.json。检查字节后确认翻译 CSV 以 EF BB BF 开头，参考 DictReader 使用默认编码，BOM 留在首列表头。

改为显式 utf-8-sig；未改原文件或预期类别数。这个失败属于验证器问题，不应写成 SQL 错误，更不能略过失败报告后宣称首轮全部通过。
